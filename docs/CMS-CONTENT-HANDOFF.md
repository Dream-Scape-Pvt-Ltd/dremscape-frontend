# Frontend content and CMS handoff

The frontend now separates sample design data from published CMS trips. Keep all preview dates, seat counts, prices and route outlines marked as examples. Do not expose preview departures through the booking endpoint.

## Keep editable in the existing admin

- `Trip` plus itinerary days: trek and tour title, category, destination, overview, facts, photos, day-by-day plan, packing and inclusions. The frontend admin journey editor can create inactive drafts; its sample import starts inactive.
- `ActivityCategory`: editable name, slug, description and visibility. The frontend admin Settings tab now has a category editor. Published tour menu labels are read from this endpoint when available.
- `TripDeparture`: dates, price, capacity and availability. Only actual records should be bookable. The local frontend preview calendar deliberately uses non-bookable example cards.
- `Destination`: name, slug, country, region name, photo and visibility. The frontend has a destination editor, but some of its editorial fields do not yet exist in the current Django serializer.
- `TrekGuide`: the people who lead treks. Their names, roles, portraits, biographies, experience, languages, certifications, regions, linked treks, display order and publish status are already editable in the Guides admin and stored by Django. This is separate from the Journal editor for travel articles.
- `TravelGuide`: Journal articles and their images, sections and publish status remain editable in the existing Blog Management admin.

Keep the existing website-settings controls for practical content such as homepage text and images, company/team information, gallery images, partner details and office location. The frontend already exposes these controls, but this checkout of Django has no `content/site-settings/` endpoint. Those settings therefore cannot be claimed as persistently editable until the backend owner adds the endpoint and a save/reload/public-page check passes. Do not remove the controls or replace them with a policy editor while this integration is completed.

## Backend fields/endpoints needed for trip editing

1. **Nepal region records.** Store each of the five broad trekking groups with `slug`, `name`, `short_name`, `introduction`, ordered `highlights`, `hero_photo`, `photo_alt`, `photo_credit`, `photo_permission_note`, `is_published`, and ordered sub-areas (`name`, `search_term` or linked destination). Expose a public list and admin create/update endpoint. Route listings should continue to use each trip's CMS destination, with an explicit region relationship or mapping.
2. **Destination editorial fields.** The frontend currently expects `headline`, `description`, `highlights`, `trail_style`, `pace`, `mood`, `base` and `gallery_images`. Add these fields to the model and public/admin serializers, or remove the controls before promising persistence.
3. **Tour category relationships.** Keep `ActivityCategory` as the source for luxury, sightseeing, wildlife, day and helicopter tours; assign each tour a category in `Trip`. The frontend uses the existing category slug for filtering. When adding new categories, keep slugs stable so shared links continue to work.
4. **Secondary trek classification.** Each trip keeps one primary CMS destination/geographic home. Add an ordered `editorial_tags` array or a many-to-many tag relation to the trip read/write serializers and admin editor. Stable slugs used by the frontend are `popular-trek`, `restricted-area`, `off-the-beaten-path`, `monsoon-rainshadow`, `short-trek`, `family-suitable`, `high-altitude`, `base-camp`, `circuit`, `cultural`, and `remote-wilderness`. These describe themes and route traits; they must never substitute for the destination relationship. The frontend can already read these slugs for search and filtering, while its sample assignments are preview-only. The current backend model cannot save them.
5. **Per-image provenance.** The current trip model stores only `hero_image_url` and `gallery_images` URLs. Add per-image `location`, `credit`, `permission` (or licence record), and descriptive `alt` fields with read/write support. The upload/editor flow should validate them, save them, reload them, and warn when any are missing. Do not infer the location or license from a filename. The current frontend editor shows an unverified-image warning until this storage exists.
6. **Public draft isolation.** The backend trip list currently filters `is_active`, but the direct trip detail and per-trip departure endpoints do not. They must return 404 for inactive trips to anonymous visitors. The frontend now guards its own catalogue and detail responses, but the public backend endpoints need the same rule so direct API calls cannot expose drafts. Public category/destination lists and sitemap inputs must exclude inactive records as well.

## Current frontend additions requiring backend follow-through

- **Peak Climbing and Expedition Climbing:** the public Climbing menu and catalogue now have separate collections. They use each trip's assigned CMS `ActivityCategory`, not its title. Create the `peak-climbing` category through the existing category endpoint and assign peak climbs to it. The existing `mountain-expedition` category fills Expedition Climbing. Keep category slugs stable. The Everest and Annapurna expedition cards are local-only design examples and importable CMS draft templates. Their duration values are layout placeholders; replace all route, safety, duration, price and photo details with approved information before publishing. No peak route has been invented while company content is pending.
- **Bhutan places:** editors can add another `Destination` with `country=BHUTAN`; the Bhutan landing page groups those places and gathers published trips assigned to them. This uses the existing country relationship as a practical grouping. For a true nested destination hierarchy, add an optional `parent_destination` self-reference, validate that parent and child share a country and that cycles are impossible, and expose it in the public/admin list and detail serializers. Then have the frontend use that relationship instead of slug/country inference.
- **Destination editorial details and altitude:** the admin form currently includes headline, description, highlights, trail style, pace, base, mood and gallery image URLs. Django's `Destination` model and serializers currently drop all of them. Add these fields plus nullable `altitude_meters` (confirmed elevation of a specific place; a whole country has no single altitude) to the model, migration, read serializers and write serializer. The **list** serializer must include the fields because the public destination page and the admin list read that endpoint. Until then, the admin checks the reloaded record and refuses to claim missing details were saved; it warns before entering altitude when support is not confirmed.
- **Company leadership:** the frontend website-settings form already contains CEO/chairman and co-founder portraits, roles, biographies and the CEO message via `company_content.team_profiles` and `company_content.ceo*`. This backend checkout does not implement `GET/PATCH content/site-settings/`. Add persistent storage and those endpoints with admin-only writes, returning the complete saved settings. The frontend now shows this form as read-only when the endpoint is unavailable and verifies a fresh read after any save. Do not replace these profiles with trek-guide records; they are different people/content types.

For each new field, save in the admin, reload, and check both the admin value and the intended public page. Create a published Bhutan place and a published trip assigned to it; verify the Bhutan hub, the place page and `/treks?country=bhutan` show that trip, while an unrelated country's trip and inactive draft stay out. Reassign the trip and check that old links stop matching. Check both climbing collections with one published trip in each CMS category and with an empty database.

The privacy policy, terms and other fixed legal pages remain reviewed site copy; they do not need CMS fields. FAQ editing is optional later work. Guide profiles, Journal stories, trip information and other practical content listed above must keep their existing admin workflows. Company and gallery controls are already present in the website-settings editor; their backend persistence is the gap to close, rather than a reason to remove the CMS interface.

Current checks and their limits are recorded in [Trip CMS acceptance status](TRIP-CMS-ACCEPTANCE-RESULTS.md).

## Acceptance checks for the integration

- Save every supported trip fact in the admin, reload, and confirm the saved value remains and appears on the intended public trip or collection page.
- Keep drafts out of the published catalogue, departures, search index and sitemap. Test this with the backend unavailable and with an empty database; neither state should turn sample trips into live offers.
- Validate image location, credit, permission and alt text alongside the upload. Display missing provenance as an editorial warning rather than silently treating the photo as verified.
- Confirm region and category links still return only matching published records after trip assignments change.
- For a draft trip, check direct detail and departures URLs as an anonymous visitor, not only the catalogue page. Verify that activating, deactivating, moving the destination and changing the category updates public search and regional/category pages after cache expiry or invalidation.

The frontend may show fallback text and sample photos while these fields are absent, but should always give published CMS records precedence. Booking, payments and actual seat availability remain separate backend work.
